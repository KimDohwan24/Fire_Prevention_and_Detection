배경

JWT 발급/검증(auth.py)·로그인 경로를 점검해서 4개 findings 를 뽑았다. 이 문서는 그중 2번(권한·자격 변경이 세션에 반영 안 됨)과 3번(키 비교 타이밍)의 수정 내용이다.

■ 1. 권한·비밀번호가 바뀌어도 기존 토큰이 살아 있었다

권한 검사(admin_required)는 DB 가 아니라 토큰에 박힌 user_role 클레임을 본다. PUT /api/users 로 role 을 바꿔도 이미 발급된 토큰의 클레임은 옛 값 그대로라, 강등당한 사람은 만료(기본 12시간)까지 관리자 API 를 계속 쓸 수 있었다. 비밀번호 변경도 마찬가지였다 — 도난당한 기기의 세션은 비밀번호 변경만으로는 회수되지 않았다.

해결: 세 변경 지점에서 user_token_valid_from 기준선을 세운다. 기준선보다 옛날에 발급된(iat 가 작은) 토큰은 401 TOKEN_REVOKED 로 거부된다 (auth._assert_not_revoked, 매 요청 SQL 대조).

정지(SUSPENDED)·탈퇴(WITHDRAWN)는 기존부터 폐기하고 있었다.

정책 전환 기록. 예전에는 "비밀번호를 바꿔도 토큰은 살아있다"가 명시적 방침이었고(test_password_change_keeps_existing_tokens_alive), 그 테스트가 방침 뒤집힘을 알리는 경비병 역할을 했다. 이번에 방침을 뒤집으면서 테스트도 ..._revokes_existing_tokens 로 교체했다.
부작용(의도됨): 비밀번호 변경 요청을 보낸 그 기기 포함 전 세션이 끊긴다. 프론트는 직후 401 TOKEN_REVOKED 를 받고 로그인 화면으로 돌아가면 된다 — 명세에 이미 있는 분기다.

함정: 폐기 해상도는 1초다

iat 는 정수 초, 기준선(now())은 마이크로초. 같은 초 안에서는 "직전 발급"과 "직후 발급"을 구분할 수 없어서 살리는 쪽(date_trunc('second') 절삭 후 <= 면 통과)을 골랐다. 새 테스트를 짤 때 로그인 직후 바로 폐기 조건을 밟으면 같은 초라서 토큰이 살아남아 실패한다 — _aged_token 처럼 발급 시각을 명시한 토큰으로 경계를 지정할 것(test_token_revocation.py 상단 docstring 참고).

■ 2. X-Internal-Key · X-Agency-Key 비교가 타이밍 어택에 열려 있었다

문자열 != 는 첫 불일치에서 비교를 멈추므로, 접두어가 몇 글자 맞았는지가 응답 시간 차로 새어 나간다. 같은 PC/LAN 시연 환경처럼 노이즈가 작은 곳에서는 반복 측정으로 키를 한 글자씩 복구하는 이론적 경로가 생긴다. X-Agency-Key 는 119 출동 통지 위조에 쓰이는 키라 특히 조심한다.

해결: auth._key_matches() 헬퍼로 hmac.compare_digest 상수 시간 비교로 통일. str 이 아니라 bytes 로 대조하는 것은 compare_digest 가 ASCII 밖 str 을 TypeError 로 거절하기 때문 — 이상한 인코딩 헤더로 500 이 나는 것까지 막는다. account_recovery·oauth_provider·telegram_link 는 이미 같은 패턴을 쓰고 있었으므로 auth.py 만 뒤처져 있던 상태였다. 동작 변화 없음(정상 키는 그대로 통과).
