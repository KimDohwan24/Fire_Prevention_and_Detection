1. 한 줄 결론

판정로직은 설계(발표 슬라이드 10 “고정 관측 창”)대로 동작한다. 누적·창 고정·기준미달 종료·확정 네 가지 동작을 모두 실제 영상으로 확인했고, 정상영상에서는 오탐이 한 건도 없었다. 확정 이후 알림 → 무응답 → 119 신고 → 기관 승계까지 최초 감지에서 접수까지 52.2초로 완주했다.
다만 판정로직 밖에서 결함 1건을 찾았다. 검출 전송 주소가 localhost일 때 프레임마다 약 2초를 버린다(8장). 원인은 IPv6 폴백이며 주소를 127.0.0.1로 바꾸면 사라진다. 이걸 모르면 시연에서 실시간 재생이 불가능하다.

3. 시나리오 A — 기준미달 종료 (관측 창 고정)

기본 설정(30프레임 / 60초)에서 house_fire를 흘려보냈다. 검출이 계속 들어오는 중에도 창이 60초에 닫히고 이벤트가 차례로 폐기됐다.

taipo에서도 같은 결과가 나왔다 — event 4 (11/30), event 10 (11/30) 모두 DISMISSED.

이게 왜 중요한가

창의 기준점은 event_first_detected_at이고 이후 프레임이 아무리 들어와도 움직이지 않는다. 만약 마지막 검출 기준으로 창을 쟀다면 event 5·6·7은 하나로 이어졌을 것이고 (16+11+7 = 34프레임 > 30), 시간만 충분하면 결국 확정됐을 것이다. 창 간격보다 조금씩 빠르게 튀는 신호 — 이 로직이 걸러내려던 바로 그 신호가 정확히 걸러졌다.

창이 닫힌 뒤 들어온 첫 검출은 쿨다운 없이 곧바로 새 이벤트를 열었다(5 → 6 사이 11초, 6 → 7 사이 5초). 이것도 설계대로다.

기본 설정으로는 이 PC에서 두 영상 모두 확정에 이르지 못했다. 원인이 서로 다르므로 조건을 나눠 확인했다.

두 경우 모두 임계값에 도달한 바로 그 프레임에서 확정됐고, event_detected_at이 기록됐으며, 확정 훅이 즉시 알림 발송으로 이어졌다. 확정 직후 들어온 검출은 CONFIRMED 이벤트에 누적되지 않고 새 이벤트(9, 12)를 열었다 — 이것도 설계대로다.

이미지 경로 주의. media/는 .gitignore 대상이라 위 이미지는 이 PC에만 있다. 발표 자료에 넣을 때는 파일을 따로 복사해 쓸 것.

event 11이 기본 임계값(30)으로는 확정될 수 없는 이유

속도 문제가 아니다. taipo는 30초짜리 클립이고 --fps 3으로 뽑으면 전체가 92프레임인데, 그중 검출이 잡히는 프레임이 11장뿐이다. 영상을 끝까지 다 돌려도 11을 넘을 수 없으므로 임계값 30에는 물리적으로 도달하지 못한다. 시연에 이 영상을 쓴다면 임계값을 낮춰야 한다.

8. 발견된 결함 — localhost 2초

전송 모드에서 추론 속도가 8.0 f/s → 0.5 f/s로 16배 떨어졌다. 왕복 시간을 직접 재서 원인을 좁혔다.

요청중앙값
GET /api/health @ localhost2051.7 ms
GET /api/health @ 127.0.0.115.3 ms
POST /api/internal/detections @ localhost2054.6 ms
POST /api/internal/detections @ 127.0.0.115.1 ms

원인. 백엔드는 0.0.0.0(IPv4)만 바인딩하는데 Windows에서 localhost는 ::1(IPv6)로 먼저 해석된다. IPv6 연결이 실패하고 IPv4로 재시도하기까지 약 2초가 걸린다. 엔드포인트 종류와 무관하게 일정하게 2초가 붙는 것이 그 증거다.

영향. 프레임마다 2초를 버린다. taipo 전체 처리가 33.8초 → 11.7초(2.9배)로 줄었고, 초당 3프레임 실시간 재생이 가능해졌다. 이 문제가 있는 상태에서는 실시간 시연 자체가 불가능하다.

조치. 실행 시 --api http://127.0.0.1:5000을 넘긴다. 근본적으로는 run_video.py의 기본값(FIREGUARD_API)을 127.0.0.1로 바꾸는 것을 검토할 만하다.

기각된 가설. 처음에는 run_video.py가 requests.Session을 쓰지 않아 매 프레임 새 커넥션을 여는 것이 원인이라고 봤다. 측정 결과 Session 재사용 시에도 2054 ms로 동일해 무관한 것으로 확인됐다. (Session 재사용 자체는 별개로 여전히 개선 여지가 있다.)

9. 시연 권장 설정

시연용 실행 (검증된 조합 — event 11이 이 설정으로 나왔다)

# 백엔드 — 임계값을 10으로 낮춰 기동
cd back
EVENT_THRESHOLD_FRAMES=10 .venv/Scripts/python app.py

# 가상 119 서버
cd mock-119 && python app.py

# 검출 — 주소는 반드시 127.0.0.1
cd ai-model
.venv/Scripts/python run_video.py --video samples/taipo_apartment_fire.webm \
    --send --cctv-no 1 --api http://127.0.0.1:5000 --realtime
설정값이유
--apihttp://127.0.0.1:5000필수. 없으면 프레임당 2초 손실(8장)
--realtime켬영상이 2배속으로 지나가지 않게
EVENT_THRESHOLD_FRAMES10taipo에는 검출 프레임이 11장뿐이라 기본 30은 도달 불가
ALERT_DEADLINE_SEC30 (기본)감지 → 접수 약 52초. 더 줄이려면 ESCALATION_INTERVAL_SEC도 같이 줄일 것
승계 시연1·2번 기관 ?mode=fail,
3번 ?mode=ok		실패 → 승계 → 접수를 화면에서 보여줄 수 있다

10. 한계와 남은 것

  • house_fire는 시연에 부적합하다. 고해상도라 CPU 디코딩만으로 프레임당 약 1.6초가 들어 0.6 f/s밖에 안 나온다. 실시간 재생이 불가능하므로 쓰려면 저해상도로 변환해야 한다.
  • GPU가 없다. 이번 측정은 전부 CPU 기준이다. GPU에서는 추론 시간이 줄어 여유가 생긴다.
  • 알림은 아직 모의다. SMS는 로그만 남기고(services/sms.py), PUSH는 DB 행일 뿐 실제로 밀어내는 것이 없다.
  • 이번 테스트 데이터가 개발 DB에 그대로 남아 있다. event 4~12 (event_media 101행). 발표 전에 정리할지 판단 필요.
  • 열린 채로 남은 이벤트는 없다. 마지막 실행의 잔여 이벤트 12(1/10)도 창이 닫히면서 스위퍼가 DISMISSED 처리했다.

11. 재현 방법

판정 결과 다시 조회하기

cd back
.venv/Scripts/python -c "import db; ..."   # 또는 psql

SELECT event_no, event_status, event_class,
       event_detected_frames, event_threshold_frames,
       event_first_detected_at, event_detected_at
FROM fire_event WHERE event_no BETWEEN 4 AND 12 ORDER BY event_no;

정상영상 오탐 검사 (백엔드 없이)

cd ai-model
.venv/Scripts/python run_video.py --video samples/normal_cctv.mp4

정상영상 새로 받기 (ITS 개방 CCTV)

스트림 주소에 시간 제한 토큰이 박혀 있어 받자마자 바로 열어야 한다. 조회는 ITS_API_URL + CCTV_API_KEY(루트 .env), 저장은 OpenCV로 한다.

이 문서의 모든 수치는 fireguard DB와 실행 로그에서 뽑은 실측값이다. 추정치나 계산값이 아니다.
