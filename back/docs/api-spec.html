1. 공통 규칙

Base URL

http://localhost:5000/api
⚠️ 예외 하나 — 미디어 파일 서빙만 /api 아래가 아니라 /media/<path> 로 붙는다. media_url · thumbnail_url 에 저장된 값이 그대로 URL 이 되게 하기 위해서다 (10. 미디어 파일 서빙).

표기 규칙

  • 모든 JSON 키는 snake_case (DB 컬럼명과 동일)
  • 모든 날짜/시간은 ISO 8601 문자열: "2026-08-08T14:30:00"
  • 신뢰도(confidence)는 0~1 사이 소수: 0.9123
  • 좌표(lat/lng)는 소수: 37.5665, 126.9780

인증

로그인 시 발급되는 JWT를 모든 요청 헤더에 포함한다. (🔒 표시된 API)

Authorization: Bearer <access_token>

토큰 유효기간은 JWT_EXPIRES_HOURS(기본 12시간)이며, 만료 시 401 TOKEN_EXPIRED다.

인증 방식은 3가지다. 프론트가 쓰는 것은 첫 번째뿐이다.

대상방식해당 API
프론트엔드 (사람)Authorization: Bearer <JWT>/api/** 전체 (/api/auth/login, /api/health 제외)
AI 모델 (내부 시스템)X-Internal-Key: <INTERNAL_API_KEY> — JWT 아님/api/internal/** (9번)
브라우저 <img>/<video>없음 (의도된 시연 범위 결정)/media/** (10번)

4. 연동 카메라 (CCTV)

먼저 읽을 것 — cctv_stream_url 은 조회할 때마다 최신화된다

⚠️ cctv_stream_url 은 DB 에 저장된 값을 그대로 주는 것이 아니다. 조회하는 그 시점에 국가교통정보센터(ITS)에서 최신 주소를 받아 갈아끼운 값이 내려간다. 적용 대상은 세 곳이다 — GET /api/cctvs · GET /api/cctvs/<cctv_no> · GET /api/internal/cctvs (9번).
  • 왜 — ITS 가 내려주는 스트림 주소에는 시간 제한 토큰(wmsAuthSign)이 박혀 있다. 저장해 두면 시간이 지나 만료되고, 그 주소는 더 이상 재생되지 않는다.
  • 매칭 방식 — cctv_name 정확 일치다. ITS 목록에서 이름이 같은 카메라를 찾아 그 주소로 바꾼다. 이름이 매칭되지 않는 카메라(수동 등록한 자체 카메라 등)는 손대지 않고 저장된 주소를 그대로 돌려준다. 별도의 "ITS 카메라 여부" 플래그는 없다.
  • DB 반영 — 주소가 실제로 바뀐 경우에만 cctv 행도 함께 갱신한다. 같은 값이면 UPDATE 하지 않는다.
  • 캐시 — 같은 영역(조회 대상 카메라를 덮는 박스) 조회 결과를 CCTV_URL_TTL_SEC(기본 300초) 동안 재사용한다. 몇 초 간격으로 폴링해도 외부 API 호출이 늘어나지 않는다.
💡 부분 실패는 허용된다 — 설정된 도로 유형(ITS_ROAD_TYPES, 기본 ex,its) 중 일부가 0건이거나 조회에 실패해도, 성공한 유형의 결과로 갱신을 진행한다. 0건은 오류가 아니라 정상 응답이다 — 그 영역에 해당 유형(고속도로/국도) 카메라가 없을 뿐이다. 모든 유형이 실패했을 때만 저장된 주소로 폴백한다.
폴백하더라도 응답은 언제나 200이다. 외부 API 가 죽었다고 카메라 조회가 실패하지는 않으므로 프론트가 별도의 에러 처리를 할 필요가 없다 (다만 그때 내려간 주소는 만료된 것일 수 있다).
🔁 프론트·AI 공통 지침 — 재생이 끊기면 CCTV 정보를 다시 조회해 새 주소로 재연결할 것. 프론트는 GET /api/cctvs/<cctv_no>, AI 모델은 GET /api/internal/cctvs?cctv_status=ACTIVE 를 다시 부르면 된다. 재조회 주기를 CCTV_URL_TTL_SEC(기본 5분)보다 촘촘하게 잡아도 캐시 때문에 같은 주소가 돌아오므로 이득이 없다.

💡 cctv_stream_url 재생 방법 (HLS)
이 값은 HLS 스트림 주소(.m3u8) 다. 백엔드는 영상을 중계하지 않고 주소 문자열만 전달하므로, 프론트가 카메라(또는 스트리밍 서버)에 직접 연결해 재생한다.
  • Safari · iOS 는 <video src="..."> 로 바로 재생된다.
  • Chrome · Firefox 는 네이티브 지원이 없어 hls.js 가 필요하다: hls.loadSource(cctv_stream_url); hls.attachMedia(videoEl);
  • CORS: hls.js 는 .m3u8 과 .ts 조각을 XHR 로 가져오므로, 스트리밍 서버가 프론트 오리진을 허용해야 한다 (막히면 재생 자체가 실패).
  • 지연: HLS 특성상 5~15초 늦다. AI 는 원본 프레임을 실시간으로 보므로 화재 알림이 영상보다 먼저 도착할 수 있다 — 정상 동작이다.
  • 스트림 주소가 사설망(192.168.x.x)이면 프론트를 띄운 PC 가 같은 네트워크에 있어야 한다.
  • 토큰 만료: ITS 카메라의 주소에는 시간 제한 토큰이 붙어 있어 오래 켜두면 조용히 끊긴다. 이 응답의 주소는 조회 시점에 최신화된 값이므로, 끊겼을 때는 CCTV 정보를 다시 조회해 새 주소로 재연결하면 된다 (스트림 주소 최신화).

6. 관리자 알림 (Alerts)

알림 흐름 (v0.3 확정 — 동시 발송, 단계 승격 없음)

이벤트가 CONFIRMED로 확정되면 백엔드는 그 CCTV 의 소유자(cctv.user_no) 한 사람에게 알림을 만든다. ADMIN 전체 브로드캐스트는 없다.

  1. 알림 행 2개를 동시에 만든다 — PUSH와 SMS. 같은 트랜잭션에서 한 번에 INSERT 하므로 alert_sent_at과 alert_deadline_at이 두 행 모두 완전히 같은 값이다. alert_level은 둘 다 1. 실제 문자 발송은 SMS 행에 대해서만 일어나고, PUSH 는 프론트가 GET /api/alerts 폴링으로 가져간다.
  2. 유예는 한 번뿐이다 — alert_deadline_at = alert_sent_at + ALERT_DEADLINE_SEC (기본 30초). 이 유예가 지나면 다음 단계는 119 신고다. 1차→2차 SMS 같은 승격 단계는 없다.
  3. 응답은 이벤트 단위로 적용된다 — 사용자가 PUSH 든 SMS 든 한쪽에만 응답하면, 같은 이벤트의 나머지 미응답 알림도 같은 상태·같은 alert_responded_at으로 함께 닫힌다. 같은 사람의 같은 화재 건이기 때문이다. 이미 닫힌 형제 알림에 다시 응답하면 409 ALREADY_RESPONDED.

그 다음 갈림길은 셋뿐이다.

사용자 행동알림 상태119 신고
READ (화재 확인) — SENT 상태에서 두 알림 모두 READ 즉시 시작 — report_trigger_reason = USER_CONFIRMED
CANCEL (오탐 취소) — 마감 전에만 가능 두 알림 모두 CANCELED 영원히 없음 — 에스컬레이션도 이 이벤트를 건너뛴다
무응답으로 유예 마감 경과 이벤트의 미응답 알림 전부 NO_RESPONSE 자동 시작 — report_trigger_reason = NO_RESPONSE_TIMEOUT

무응답 처리는 백엔드 스케줄러가 ESCALATION_INTERVAL_SEC(기본 5초)마다 도는 에스컬레이션 스윕이 담당한다. 프론트가 호출할 API 는 없다. 스윕은 관측 창이 닫히도록 임계값을 못 채운 PENDING 이벤트를 DISMISSED로 정리하는 일도 함께 한다.

💡 늦은 READ — 이미 NO_RESPONSE가 된(=119 신고까지 진행된) 알림에 뒤늦게 READ를 보내는 것은 허용되지만, alert_status는 NO_RESPONSE 그대로 보존되고 alert_responded_at만 기록된다. 늦은 확인이 "무응답으로 신고까지 갔다"는 이력을 지우지 못하게 하기 위해서다. 이 경우 두 번째 신고는 만들어지지 않는다.
💡 점검 모드 — event_is_test = true인 이벤트는 확정되어도 알림 행 자체가 만들어지지 않고, 에스컬레이션·119 신고 대상에서도 완전히 제외된다.

8. 119 신고 (Reports)

신고 흐름 (승계 알고리즘)

신고는 사용자가 만들지 않는다. 백엔드가 두 지점에서 자동으로 시작한다.

report_trigger_reason시작 지점
USER_CONFIRMED사용자가 SENT 알림에 READ(화재 확인)로 응답한 즉시
NO_RESPONSE_TIMEOUT유예 마감까지 무응답 → 에스컬레이션 스윕이 알림을 NO_RESPONSE로 닫으면서

시작되면 아래 순서로 돈다. 바깥 루프가 기관 승계, 안쪽 루프가 같은 기관 재시도다.

  1. 후보 기관 정렬 — agency_is_active = true인 기관을, 해당 이벤트 CCTV 의 좌표(cctv_lat/cctv_lng)로부터의 하버사인(haversine) 거리 오름차순으로 줄 세운다. 활성 기관이 하나도 없으면 신고 자체를 하지 않는다.
  2. 행 선점 — 시도할 기관마다 report_119 행을 먼저 SENDING으로 INSERT 한다. report_sequence는 1, 2, 3… 으로 올라간다. 거리는 report_distance_km(소수 3자리)에, CCTV 위치 문자열은 report_address에 남는다.
  3. 전송 (안쪽 루프) — 그 기관의 agency_endpoint로 신고 JSON 을 POST 한다. MAX_REPORT_ATTEMPTS(기본 4)회까지 시도하며, 매 시도마다 report_attempt_count가 올라간다. 타임아웃(REPORT_HTTP_TIMEOUT_SEC, 기본 3초) · 연결 실패 · 2xx 아닌 응답은 모두 실패로 보고 재시도한다.
  4. 접수 확인 — 2xx 를 받으면 그 행이 ACCEPTED가 되고 report_accepted_at이 찍힌다. 응답 본문에 external_id가 있으면 report_external_id에 저장한다 (본문 없는 2xx 도 성공으로 본다 — 이때는 null). 여기서 승계는 멈춘다.
    ⚠️ ACCEPTED는 "119 서버가 신고를 받았다"까지다. 소방차 배차 확인이 아니다 — 그건 119 가 별도 콜백으로 회신하는 값이고 아직 구현하지 않았다. 화면에 '출동'으로 표기하지 말 것.
  5. 기관 소진 → 승계 — MAX_REPORT_ATTEMPTS회를 다 쓰고도 못 받으면 그 행은 NO_RESPONSE(무응답으로 승계)로 닫고, 다음으로 가까운 기관에 대해 2번으로 돌아간다. report_sequence가 1 늘어난다.
  6. 전 기관 소진 — 마지막 기관까지 실패하면 그 마지막 행만 FAILED(전송실패)가 된다. 앞선 기관들의 행은 NO_RESPONSE로 남는다.

누적·확정 규칙
  1. 열린 이벤트 찾기 — 해당 카메라의 가장 최근 PENDING 이벤트를 찾는다.
  2. 관측 창 종료 판정 — 그 이벤트의 event_first_detected_at이 captured_at보다 EVENT_WINDOW_SEC(기본 60초) 넘게 오래됐으면 창이 닫힌 것이므로 그 이벤트를 DISMISSED(기준미달)로 닫고 없는 것으로 취급한다. 이 프레임은 새 이벤트의 최초 감지 프레임이 된다(쿨다운 없음). 같은 정리를 에스컬레이션 스윕도 주기적으로 수행하므로, 다음 프레임이 오지 않아도 창이 닫히면 정리된다.
    창의 기준점은 최초 감지 시각이며 이후 검출로 연장되지 않는다. 마지막 검출 기준으로 재면 창이 매번 늘어나서, 창보다 조금씩 빠르게 튀는 신호가 시간만 충분하면 결국 확정된다 — 이 규칙이 걸러내려는 신호가 바로 그것이다.
  3. 비화재 프레임 — flame/smoke가 하나도 없으면 누적도 미디어 저장도 하지 않는다. 열린 이벤트가 없으면 {"event_no": null, "ignored": true}, 있으면 현재 상태를 그대로 돌려준다.
  4. 이벤트 생성 / 누적 — 열린 이벤트가 없으면 PENDING 이벤트를 새로 만들고 (event_detected_frames = 1), 있으면 +1 한다. event_class는 병합되고(FLAME + SMOKE → FLAME_SMOKE), event_confidence는 지금까지의 최고값을 유지한다.
  5. 미디어 저장 — 화재 프레임은 event_media에 media_type = FRAME으로 저장되고, detections 배열은 원본 그대로 media_detections에 들어간다. 지금까지 중 가장 신뢰도가 높은 프레임이 대표 이미지(media_is_primary)로 교체된다.
  6. 확정 — event_detected_frames >= event_threshold_frames가 되는 순간 CONFIRMED로 바뀌고 event_detected_at이 찍히며, 곧바로 알림 발송(PUSH+SMS)이 이어진다 (6번).
💡 event_threshold_frames는 이벤트를 만드는 순간의 EVENT_THRESHOLD_FRAMES(기본 30) 값을 그 이벤트 행에 복사해 둔 것이다. 설정을 바꿔도 이미 열려 있는 이벤트의 기준은 바뀌지 않는다. 확정된 이벤트는 더 이상 "열린 이벤트"가 아니므로, 그 다음 화재 프레임은 새 이벤트를 연다.

⚠️ 인증을 걸지 않은 것은 의도된 시연 범위의 결정이다. 브라우저의 <img>/<video> 태그는 Authorization 헤더를 붙일 수 없어서 JWT 를 요구하면 화면에 이미지가 뜨지 않는다. 운영 환경이라면 (1) 만료 시간이 든 서명 URL(signed URL)을 발급하거나 (2) nginx 등 리버스 프록시에서 인증 후 내부 리다이렉트(X-Accel-Redirect)로 넘기는 방식이 필요하다. 지금 구조는 경로만 알면 누구나 파일을 열 수 있다는 뜻이니 그대로 배포하지 말 것.
💡 thumbnail_url이 가리키는 것 — 해당 이벤트의 대표 프레임 (media_is_primary = true) 중 media_confidence가 가장 높은 것, 동점이면 media_no가 작은 쪽(= 먼저 저장된 프레임)이다. 대표 프레임이 없으면 null이 내려온다.
