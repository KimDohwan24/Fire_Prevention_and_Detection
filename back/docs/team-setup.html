1. 모두 공통 — 개발 환경 준비

백엔드를 직접 만지지 않더라도, 서버를 띄울 수 있어야 프론트·AI 작업을 검증할 수 있습니다. 전원 아래 5단계를 한 번씩 해두세요.

1) 저장소 클론

git clone https://github.com/KimDohwan24/Fire_Prevention_and_Detection.git
cd Fire_Prevention_and_Detection
git checkout dev-Wang

2) 파이썬 가상환경 + 의존성

cd back
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt
💡 Mac · Linux 는 .venv/bin/pip 입니다. 아래 예시들의 .venv/Scripts/ 도 모두 .venv/bin/ 으로 바꿔 읽으세요.
파이썬은 3.11 이상을 권장합니다 (3.14 에서 동작 확인).

3) PostgreSQL 데이터베이스 만들기

pgAdmin 이나 psql 에서 데이터베이스를 먼저 만들고, 그 안에서 스키마 스크립트를 실행합니다.

-- 1. 데이터베이스 생성 (이름은 반드시 fireguard)
CREATE DATABASE fireguard;

-- 2. fireguard 데이터베이스에 접속한 뒤, db/schema.sql 파일 내용을 통째로 실행
⚠️ db/schema.sql 첫 줄이 DROP SCHEMA IF EXISTS fireguard CASCADE; 입니다. 기존 데이터가 전부 지워집니다. 이미 쓰던 DB 가 있다면 실행 전에 확인하세요.
💡 초기에 DB 이름을 firegaurd (오타) 로 만든 사람이 있습니다. 이름을 맞추려면:
ALTER DATABASE firegaurd RENAME TO fireguard; (접속을 모두 끊은 뒤 실행)

4) 환경변수 파일 만들기

.env.example 을 복사해서 .env 를 만들고 자기 값을 채웁니다.

cp .env.example .env
항목설명
DB_PASSWORD필수. 본인 PostgreSQL 비밀번호
DB_USER보통 postgres
JWT_SECRET아무 문자열. 개발용이면 값이 있기만 하면 됨
CCTV_API_KEY선택. 국가교통정보센터(its.go.kr) 인증키. CCTV 스트림 주소를 최신 값으로 갱신할 때만 씁니다. 비워 두면 외부 호출 없이 DB 에 저장된 주소를 그대로 쓰므로, 없어도 개발·테스트는 됩니다
INTERNAL_API_KEYAI ↔ 백엔드 통신 키. 비워두면 개발용 기본값 사용
⚠️ .env 는 깃에 올라가지 않습니다(.gitignore). 실제 키·비밀번호를 .env.example 에 적지 마세요. 템플릿은 항상 값이 빈 상태로 커밋합니다.

실시간 알림 — 폴링하지 않습니다 (2026-08-11 확정)

⚠️ 이전 판의 "3~5초 폴링 권장"은 폐기됐습니다. 폴링 코드를 이미 넣으셨다면 빼주세요. 프론트에 물어보던 "폴링으로 갈까요?" 항목도 닫혔습니다 — 답하실 필요 없습니다.

기다렸다가 알려줄 상태 변화가 없기 때문입니다. 119 신고는 사용자가 화재확인을 누른 POST /api/alerts/<alert_no>/respond 요청 안에서 동기로 끝납니다. 그 응답이 돌아온 시점에 신고는 이미 접수됐거나 실패해 있습니다.

화면이 알아야 할 것어떻게 얻나
새 화재 알림이 왔다 SMS가 사용자를 깨웁니다(실제로 발송되는 유일한 채널). 문자를 보고 앱을 열면 그때 GET /api/alerts 를 한 번 부르면 됩니다
남은 유예 시간(카운트다운) 응답에 실린 alert_deadline_at 으로 클라이언트가 로컬 계산합니다. 서버에 다시 물을 필요가 없습니다
119 접수 결과 화재확인 요청의 응답으로 확정됩니다 (동기)

화면 갱신 원칙: 열 때 조회 + 행동 후 갱신. setInterval 로 주기 조회하지 마세요.

// 화면을 열 때 한 번, 그리고 응답 등 행동 직후에 다시 부른다
const loadAlerts = async () => {
  const res = await fetch(`${BASE}/api/alerts?alert_status=SENT`, {
    headers: { Authorization: `Bearer ${token}` },
  });
  const { items } = await res.json();
  // 남은 시간은 items[i].alert_deadline_at 으로 로컬에서 계산해 표시
};

useEffect(() => { loadAlerts(); }, []);        // 열 때 1회
await respond(alertNo, 'READ'); await loadAlerts();  // 행동 후 갱신

※ 유일한 예외 상황: 화면을 켜둔 채 응답하지 않아 유예가 지나간 경우, 서버가 대신 신고한 결과는 화면을 다시 열거나 새로고침해야 보입니다. 이 한 경우 때문에 상시 폴링을 두지는 않기로 했습니다.

계정 찾기 — 아이디 찾기 · 비밀번호 재설정 (2026-08-11 신규)

✅ 세 엔드포인트가 구현됐습니다. FindAccount.jsx 의 "시뮬레이션 처리 (가상 결과)" 코드를 실제 호출로 바꾸시면 됩니다. 전부 비로그인 상태로 부르는 공개 API 입니다.
엔드포인트보내는 것 → 받는 것
POST /api/auth/find-id user_name, user_email → { "user_id": "adm****" }
부분 마스킹돼 나갑니다(앞 3자만). 못 찾으면 404
POST /api/auth/password-reset/request user_id, user_name, user_email → 인증코드를 SMS 발송
POST /api/auth/password-reset/confirm user_id, code, user_pw → 변경 완료

비밀번호 찾기 흐름이 2단계 → 3단계가 됩니다. 정보 확인 → 인증코드 입력(신규) → 새 비밀번호 설정.

  • request 는 정보가 틀려도 200 입니다. 계정이 있는지 없는지를 응답으로 흘리지 않기 위해서입니다. "정보가 일치하면 문자를 보냈습니다" 라고 안내하고 바로 코드 입력 화면으로 넘기시면 됩니다 — 성공/실패로 분기하지 마세요.
  • 코드는 응답에 들어있지 않습니다. 실제로 SMS 로만 나갑니다. 지금은 목(mock) 발송기라 백엔드 서버 콘솔 로그에 찍히니, 개발·시연 중에는 그걸 보고 입력하시면 됩니다.
  • 코드는 10자리, 대소문자·공백 무관합니다. 사용자가 소문자로 치거나 중간에 공백을 넣어도 통과하니 입력칸에서 굳이 막지 마세요. 유효시간은 약 5분입니다.
  • 새 비밀번호에는 가입과 똑같은 규칙이 적용됩니다 — 영문+숫자+특수문자 3종 포함 8~64자. MyPage 의 "최소 4자리" 검증은 백엔드 규칙과 어긋납니다(통과시켜도 백엔드가 400을 냅니다). 같이 맞춰주세요.
  • 코드가 틀렸을 때와 아이디가 없을 때가 같은 응답(INVALID_RESET_CODE)입니다. 구분해 안내할 수 없습니다.

등록할 카메라 고르기 — ITS 공공 CCTV 목록 (2026-08-11 신규)

✅ GET /api/its/cctvs 가 구현됐습니다. 프론트에 하드코딩해 둔 ITS 목록 배열(ITS_PUBLIC_CCTVS)과 "백엔드 미구현" 안내 문구는 이제 지우셔도 됩니다.

DB 가 아니라 ITS 오픈 API 를 그 자리에서 조회해 돌려줍니다. 응답은 { "items": [...] } 이고, 필드는 우리 스키마 이름으로 정규화돼 있어 그대로 POST /api/cctvs 에 넘기면 등록됩니다.

쿼리 파라미터설명
q카메라 이름 부분 일치 검색 (서버에서 필터링)
min_x max_x min_y max_y 조회 영역(경도 min/max, 위도 min/max). 네 개를 전부 보내거나 전부 생략해야 하며, 일부만 보내면 400 입니다. 생략하면 전국을 조회합니다
  • is_registered 를 꼭 쓰세요 — 이미 우리 DB 에 있는 카메라인지 알려줍니다. true 인 항목은 "등록" 버튼을 막아 중복 등록을 예방하시면 됩니다.
  • 실패는 502 로 옵니다(ITS_UNAVAILABLE). 카메라 목록 API 와 달리 폴백할 저장분이 없어서, 빈 목록으로 위장하지 않고 실패를 알립니다. 화면에는 "조회 실패, 잠시 후 재시도" 로 안내해주세요. 0건은 정상 200 이니 "검색 결과 없음" 과 구분해 처리하시면 됩니다.
  • 좌표는 cctv_lat(위도)·cctv_lng(경도)로 정규화돼 있습니다. ITS 원본은 coordy=위도, coordx=경도라 헷갈리는데 백엔드에서 이미 바로잡았습니다.

CCTV 영상 재생 — HLS

cctv_stream_url 은 HLS(.m3u8) 주소입니다. 백엔드는 영상을 중계하지 않고 주소만 전달하므로, 프론트가 직접 연결해 재생합니다.

import Hls from 'hls.js';

const hls = new Hls();
hls.loadSource(cctv.cctv_stream_url);
hls.attachMedia(videoEl);
  • Safari · iOS 는 hls.js 없이 <video src="..."> 로 바로 재생됩니다.
  • 지연이 5~15초 있습니다. AI 는 원본 프레임을 실시간으로 보므로 알림이 영상보다 먼저 도착할 수 있습니다 — 버그가 아닙니다.
  • 스트림 주소에 만료되는 인증 토큰이 붙어 있어, 오래 켜두면 끊길 수 있습니다. 끊기면 CCTV 정보를 다시 조회해 새 주소로 재생하세요.
  • 백엔드가 이미 조회할 때마다 최신 주소로 갈아끼워 내려줍니다 (GET /api/cctvs · GET /api/cctvs/<cctv_no> 둘 다). 그래서 끊겼을 때의 대응은 CCTV 정보를 다시 조회해서 받은 cctv_stream_url 로 다시 붙이는 것뿐이고, 토큰 갱신 같은 특별한 처리는 프론트에서 할 게 없습니다. 외부 조회가 실패해도 응답은 항상 200 이라 에러 분기도 필요 없습니다.

검출 이미지 표시

이벤트 목록의 thumbnail_url, 상세의 media[].media_url 은 그대로 <img src> 에 넣으면 됩니다 (API 주소만 앞에 붙여서). 인증 헤더가 필요 없습니다.

검출 상자를 그리려면 media_detections 의 box 값을 쓰세요. [중심x, 중심y, 너비, 높이] 이며 0~1 비율이므로, 이미지 실제 크기를 곱해서 좌표로 바꿉니다.

  • CCTV 스트림(HLS)에서 프레임을 읽어 검출 → 결과를 백엔드로 전송
  • 스트림이 끊기면 GET /api/internal/cctvs?cctv_status=ACTIVE 로 주소를 다시 받아 재연결하는 루프 구현 (아래 "카메라 목록 받아오기" 참고)
  • 검출 프레임 이미지를 media/ 아래에 저장 (백엔드가 그 경로를 서빙)

카메라 목록 받아오기 — 끊긴 스트림을 되살리는 곳

감시할 카메라와 지금 유효한 HLS 주소는 아래 API 로 받습니다. 검출 전송과 같은 X-Internal-Key 헤더를 씁니다 (JWT 아님).

GET http://localhost:5000/api/internal/cctvs?cctv_status=ACTIVE
X-Internal-Key: <INTERNAL_API_KEY 값>

{
  "items": [
    {
      "cctv_no": 1,
      "cctv_name": "정문 카메라",
      "cctv_lat": 37.5665, "cctv_lng": 126.9780,
      "cctv_stream_url": "http://cctvsec.ktict.co.kr/9999/EXAMPLE.stream/playlist.m3u8?wmsAuthSign=FAKE-TOKEN-FOR-DOCS",
      "cctv_status": "ACTIVE"
    }
  ]
}
  1. 기동할 때 한 번 호출해 감시 대상(cctv_no ↔ cctv_stream_url)을 잡습니다.
  2. 스트림 읽기가 실패하면 이 API 를 다시 호출하고, 해당 cctv_no 의 cctv_stream_url 을 꺼내 그 주소로 재연결합니다.
💡 여기 내려오는 주소는 백엔드가 조회 시점에 최신화한 값입니다 (저장해 둔 값이 아님). 다만 결과가 5분(CCTV_URL_TTL_SEC) 동안 캐시되므로 5분보다 자주 다시 불러도 같은 주소가 돌아옵니다 — 주기적으로 폴링할 이유가 없고, 끊겼을 때만 다시 부르면 충분합니다. 외부 조회가 실패해도 이 API 는 항상 200 이므로 별도 에러 분기는 필요 없습니다. 자세한 규칙은 Swagger UI 의 GET /api/cctvs 설명을 보세요.

백엔드가 가정한 전송 형식

프레임 하나당 한 번 호출합니다. 불이 났는지 아닌지 판정하는 것은 백엔드가 합니다 — AI 는 "이 프레임에서 무엇이 보였는지"만 보내면 됩니다.

POST http://localhost:5000/api/internal/detections
Content-Type: application/json
X-Internal-Key: <INTERNAL_API_KEY 값>

{
  "cctv_no": 1,
  "captured_at": "2026-08-10T14:30:00",
  "media_url": "/media/events/raw/f001.jpg",
  "detections": [
    { "cls": "flame", "conf": 0.91, "box": [0.238, 0.259, 0.047, 0.113] },
    { "cls": "person", "conf": 0.77, "box": [0.412, 0.688, 0.031, 0.142] }
  ]
}
항목설명
clsflame · smoke 는 화재로 집계. 그 외(person 등)는 저장만 하고 판정에는 쓰지 않음
conf신뢰도 0~1
boxYOLO xywhn 형식 (중심x, 중심y, 너비, 높이 — 0~1 비율)
불이 없는 프레임detections 를 빈 배열로 보내도 됩니다
💡 판정 규칙: 최초로 화재가 검출된 순간부터 EVENT_WINDOW_SEC(기본 60초) 관측 창이 열리고, 그 창 안에서 검출이 일정 프레임 수(EVENT_THRESHOLD_FRAMES, 기본 30) 만큼 쌓이면 화재 확정(CONFIRMED) 되고 자동으로 알림이 나갑니다. 창은 최초 감지 시각에 고정되어 이후 검출로 연장되지 않으며, 미달인 채로 창이 닫히면 기준미달(DISMISSED)로 정리되고 이후 검출은 새 이벤트로 다시 셉니다. 시연 때는 이 값들을 낮춰서 빨리 확정시킬 수 있습니다.
⚠️ 스트림이 조용히 죽는 것이 가장 위험합니다. HLS 주소의 토큰이 만료되면 에러도 알림도 없이 감시만 멈춥니다. 스트림 읽기가 실패하면 반드시 GET /api/internal/cctvs?cctv_status=ACTIVE 를 다시 호출해 새 cctv_stream_url 로 재연결하세요.

5. 시연 준비 (다 같이)

가상 119 서버 띄우기

실제로 119 에 신고할 수는 없으므로, 소방청 접수 서버를 흉내내는 서버를 함께 띄웁니다.

cd mock-119
../back/.venv/Scripts/python app.py     # 포트 6000

신고가 도착하면 이 콘솔에 한글 로그가 찍히므로, 시연 화면에 띄워두면 좋습니다.

승계 시연 만들기

"가까운 소방서가 응답하지 않아 다음 소방서로 넘어간다"를 보여주려면, 소방서 두 곳의 endpoint 를 다르게 설정합니다.

-- 1순위(가까운) 소방서는 실패하도록
UPDATE fireguard.agency SET agency_endpoint = 'http://localhost:6000/report?mode=fail'
 WHERE agency_no = 1;

-- 2순위 소방서는 정상 접수
UPDATE fireguard.agency SET agency_endpoint = 'http://localhost:6000/report?mode=ok'
 WHERE agency_no = 2;

mode 값: ok(접수) · fail(장애) · timeout(무응답) · reject(거절)

시간 단축

기본 설정으로는 알림 후 30초를 기다려야 자동 신고가 나갑니다. 더 짧게 돌리려면 .env 를 조정하세요.

ALERT_DEADLINE_SEC=10       # 알림 유예를 10초로 (기본 30)
EVENT_THRESHOLD_FRAMES=5    # 5프레임만 쌓여도 화재 확정 (기본 30)
ESCALATION_INTERVAL_SEC=2   # 무응답 감지 주기를 2초로 (기본 5)

스윕 주기(ESCALATION_INTERVAL_SEC)만큼 신고가 늦어지므로, 유예를 짧게 잡을수록 주기도 같이 줄여야 실제 유예가 의도한 값에 가까워집니다. 기본값(유예 30초 · 주기 5초)에서 실제 유예는 30~35초입니다.

⚠️ 2026-08-10 기본값 변경 — 알림 유예가 ALERT_DEADLINE_MIN=3(3분)에서 ALERT_DEADLINE_SEC=30(30초)으로, 스윕 주기가 10초에서 5초로 바뀌었습니다. 내 .env 에 옛 이름(ALERT_DEADLINE_MIN)이나 ESCALATION_INTERVAL_SEC=10 이 적혀 있다면 지우세요. 옛 이름은 조용히 무시되고(기본 30초가 적용되므로 동작은 정상), ESCALATION_INTERVAL_SEC 는 적어 둔 값이 그대로 쓰여 혼자만 10초로 돕니다.
⚠️ 2026-08-10 DB 스키마 변경 — 기존 개발 DB 는 마이그레이션이 필요합니다

세 가지가 한 번에 바뀝니다.

  1. 신고 상태 DISPATCHED → ACCEPTED, report_dispatched_at → report_accepted_at. 2xx 응답은 "119 가 신고를 받았다"이지 "소방차가 배차됐다"가 아니라서 이름이 실제 뜻과 맞지 않았습니다.
  2. 부분 유니크 인덱스 재생성. 인덱스 조건에 'DISPATCHED' 문자열이 직접 박혀 있어서, 다시 만들지 않으면 이벤트당 진행 중 신고 1건 보장이 조용히 깨집니다.
  3. report_log 테이블 신설 — 119 송수신 이력 (전송 시도 1회에 1행). ERD v4 에 없던 테이블입니다.

기존 DB 를 유지하려면 저장소의 마이그레이션 파일을 한 번 실행하세요. SQL 원본은 db/migrations/ 한 곳에만 둡니다 — 문서에 복사해 두면 서로 어긋납니다.

db/migrations/2026-08-10-report-accepted-and-report-log.sql

방법 A — pgAdmin (권장)

  1. 왼쪽 트리에서 내 DB(보통 fireguard)를 선택 — 여기를 틀리면 엉뚱한 DB 가 바뀝니다
  2. Tools → Query Tool
  3. 폴더 아이콘(Open File)으로 위 파일을 열거나, 파일 내용을 통째로 붙여넣기
  4. 실행(F5). 마지막에 COMMIT 까지 나오면 성공입니다

방법 B — psql
psql 은 PATH 에 없는 게 보통입니다. 설치 경로를 그대로 쓰세요 (숫자는 설치한 PostgreSQL 버전 — C:\Program Files\PostgreSQL\ 를 열어 확인). 저장소 루트에서 실행해야 상대경로가 맞습니다. 비밀번호는 물어봅니다.

cd D:\Fire_Prevention_and_Detection
"C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -d fireguard ^
  -f db/migrations/2026-08-10-report-accepted-and-report-log.sql

-U 와 -d 는 자기 .env 의 DB_USER · DB_NAME 과 같은 값을 넣으세요. 기본값은 postgres · fireguard 입니다.

💡 확인 — 파일 맨 아래에 적용 확인용 조회 3개가 주석으로 들어 있습니다. 주석을 풀어 실행하면 DISPATCHED 가 0건, 인덱스 조건이 ('SENDING','ACCEPTED'), report_log 가 0행으로 나와야 합니다.
이미 적용한 DB 에 또 돌려도 안전합니다. 첫 문장에서 "report_dispatched_at 칼럼은 없습니다" 오류가 나고 나머지는 전부 무시되며 통째로 롤백됩니다. 오류가 여러 줄 쏟아지지만 DB 는 그대로입니다.
⚠️ 한글이 들어간 SQL 을 psql -c "..." 로 직접 입력하면 한국어 윈도우 콘솔(코드페이지 949)에서 인코딩 오류가 납니다. 파일로 넘기는 -f 는 문제없으니 위 방식 그대로 쓰세요.

DB 를 새로 만들 거면 db/schema.sql 하나면 되고 이 파일은 필요 없습니다. 다만 schema.sql 은 첫 줄이 DROP SCHEMA fireguard CASCADE 라 기존 데이터가 전부 사라집니다. fireguard 스키마 안에 PostGIS 를 설치해 둔 사람은 그 확장도 같이 날아가므로, 기존 DB 에는 반드시 위 마이그레이션 쪽을 쓰세요.

증상원인과 해결
서버 실행 시 DB 접속 오류 .env 의 DB_PASSWORD 가 비어 있거나 DB_NAME 이 실제 DB 이름과 다릅니다. PostgreSQL 서비스가 켜져 있는지도 확인하세요.
테스트가 DB 를 못 만든다 테스트는 postgres 유지보수 DB 에 접속해 fireguard_test 를 새로 만듭니다. DB_USER 에 DB 생성 권한이 필요합니다.
psycopg2 설치 실패 파이썬 3.14 는 psycopg2-binary 2.9.11 이상이어야 합니다. requirements.txt 에 이미 반영돼 있으니 그대로 설치하세요.
API 가 401 을 준다 토큰이 없거나 만료됐습니다. 다시 로그인해 새 토큰을 받으세요 (기본 만료 12시간, JWT_EXPIRES_HOURS).
내부 검출 API 가 401 X-Internal-Key 헤더 값이 백엔드의 INTERNAL_API_KEY 와 달라서입니다. JWT 가 아니라 이 헤더를 씁니다.
영상이 재생되지 않는다 주소가 rtsp:// 면 브라우저에서 재생 불가입니다(HLS 여야 함). HLS 인데도 안 되면 스트림 토큰 만료이거나 CORS 문제이니, CCTV 정보를 다시 조회해 보세요.
이미지가 404 파일이 media/ 아래 실제로 있어야 합니다. media_url 이 /media/events/12/f.jpg 면 파일은 media/events/12/f.jpg 에 있어야 합니다.
알림이 오지 않는다 점검 모드 이벤트(event_is_test=true)는 알림·신고가 나가지 않습니다. 또 CCTV 에 담당 사용자(user_no)가 지정돼 있어야 그 사람에게 갑니다.
신고가 두 번 나간다 나가지 않습니다. 진행 중인 신고는 이벤트당 1건만 허용되도록 DB 인덱스로 막혀 있습니다.
깃에 문서가 안 올라간다 의도된 규칙입니다. *.md 는 깃에서 제외되고, 팀 공유 문서는 .html · .sql 로 만듭니다.
