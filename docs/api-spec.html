1. 공통 규칙

Base URL

http://localhost:5000/api
⚠️ 예외 하나 — 미디어 파일 서빙만 /api 아래가 아니라 /media/<path> 로 붙는다. media_url · thumbnail_url 에 저장된 값이 그대로 URL 이 되게 하기 위해서다 (10. 미디어 파일 서빙).

표기 규칙

  • 모든 JSON 키는 snake_case (DB 컬럼명과 동일)
  • 모든 날짜/시간은 ISO 8601 문자열: "2026-08-08T14:30:00"
  • 신뢰도(confidence)는 0~1 사이 소수: 0.9123
  • 좌표(lat/lng)는 소수: 37.5665, 126.9780

인증

로그인 시 발급되는 JWT를 모든 요청 헤더에 포함한다. (🔒 표시된 API)

Authorization: Bearer <access_token>

토큰 유효기간은 JWT_EXPIRES_HOURS(기본 12시간)이며, 만료 시 401 TOKEN_EXPIRED다.

인증 방식은 3가지다. 프론트가 쓰는 것은 첫 번째뿐이다.

대상방식해당 API
프론트엔드 (사람)Authorization: Bearer <JWT>/api/** 전체 (/api/auth/login, /api/health 제외)
AI 모델 (내부 시스템)X-Internal-Key: <INTERNAL_API_KEY> — JWT 아님/api/internal/** (9번)
브라우저 <img>/<video>없음 (의도된 시연 범위 결정)/media/** (10번)

헬스체크

서버 기동 확인용. 인증이 필요 없다.

GET /api/health  →  { "status": "ok" }

공통 에러 형식

모든 에러 응답은 아래 형태로 통일한다.

{
  "code": "INVALID_CREDENTIALS",
  "message": "아이디 또는 비밀번호가 일치하지 않습니다."
}
상태코드의미
400요청 형식 오류 (필수 필드 누락, 타입 오류)
401미인증 (토큰 없음/만료)
403권한 없음 (VIEWER가 ADMIN 기능 호출 등)
404리소스 없음 (경로 자체가 없을 때는 NOT_FOUND)
405허용되지 않은 메서드 (METHOD_NOT_ALLOWED)
409상태 충돌 (중복 아이디, 이미 응답한 알림, 마감 지난 취소 등)
500서버 내부 오류 (INTERNAL_ERROR)

페이징 공통 형식

목록 API는 ?page=1&size=20 쿼리를 받고, 아래 형태로 응답한다. (page는 1부터 시작)

{
  "items": [ ... ],
  "page": 1,
  "size": 20,
  "total_count": 42,
  "total_pages": 3
}

상태값 (Enum) 정리

필드값
user_roleADMIN(관리자) · VIEWER(조회전용)
user_statusACTIVE(정상) · SUSPENDED(정지) · WITHDRAWN(탈퇴)
cctv_statusACTIVE(정상) · INACTIVE(중지) · ERROR(오류)
event_statusPENDING(판정중 — 프레임 누적 중) · CONFIRMED(확정) · DISMISSED(기준미달)
event_classFLAME(불꽃) · SMOKE(연기) · FLAME_SMOKE(둘다)
media_typeFRAME(프레임 이미지) · CLIP(영상 클립)
alert_level1 — 항상 1. 단계 승격 개념이 없어졌다 (아래 주의 참고)
alert_channelPUSH(앱알림) · SMS(문자)
alert_statusSENT(발송) · READ(확인) · CANCELED(취소) · NO_RESPONSE(무응답)
report_statusSENDING(전송중) · DISPATCHED(출동접수) · NO_RESPONSE(무응답으로 승계) · FAILED(전송실패)
report_trigger_reasonUSER_CONFIRMED(사용자가 알림에서 화재 확인) · NO_RESPONSE_TIMEOUT(유예 마감까지 무응답)
⚠️ v0.3 변경 — alert_level은 이제 항상 1이다. 이전 설계의 2(승격) · 3(최종)은 폐기했다. 확정 시 PUSH 와 SMS 가 동시에 나가므로 단계를 나눠 승격시킬 대상이 없다 (6. 관리자 알림). 컬럼 자체는 DB 스키마 호환을 위해 남겨두었을 뿐이니, 프론트는 이 값으로 정렬·분기하지 말 것. 채널 구분은 alert_channel로 한다.
💡 PENDING 이벤트는 AI 가 화재 프레임을 누적 중이지만 아직 임계값에 도달하지 않은 상태다. 알림도 신고도 나가지 않았다. 목록 API 에 그대로 노출되므로 프론트에서 "판정중" 배지로 구분해 주면 된다. 검출이 끊긴 채 EVENT_WINDOW_SEC가 지나면 자동으로 DISMISSED가 된다.

Errors
상태코드code설명
409DUPLICATE_USER_ID이미 사용 중인 아이디
비밀번호 작성규칙 근거 — 「개인정보의 안전성 확보조치 기준」 및 KISA 「패스워드 선택 및 이용 안내서」 권고를 바탕으로 한다: 영문자·숫자·특수문자 3종을 모두 포함해 8자 이상(최대 64자), 동일 문자 3회 이상 반복(aaa, 111 등)·연속 문자열 4자 이상(1234, abcd, dcba 등)· 키보드 배열 문자열(qwer, asdf 등)·아이디 포함 금지. 같은 규칙이 PUT /api/users/<user_no>의 user_pw 변경에도 적용되며, 로그인(POST /api/auth/login)에는 적용하지 않는다 (기존 계정 로그인 보장).
PUT /api/users/<user_no> 🔒 인증 필요 (ADMIN 전체 / 본인 일부)
사용자 정보 수정. 보낸 필드만 갱신한다. user_pw 포함 시 비밀번호 변경 (POST /api/users 와 동일한 비밀번호 작성규칙을 적용하며, 위반 시 400). 탈퇴 처리도 이 API로 한다: user_status=WITHDRAWN을 보내면 서버가 user_withdrawal_at을 함께 기록한다.
권한 규칙 — ADMIN은 모든 사용자의 모든 필드를 수정할 수 있다. 일반 사용자(VIEWER)는 본인 계정만 수정할 수 있으며, 허용 필드는 user_name · user_email · user_phone · user_gender · user_address · user_pw 뿐이다. user_role과 user_status는 ADMIN 전용이며, 요청 본문에 하나라도 포함되면 다른 필드까지 포함해 요청 전체가 403으로 거부된다.
Request Body (모두 선택)
{
  "user_name": "홍길동",
  "user_email": "new@fireguard.kr",
  "user_phone": "01099998888",
  "user_role": "VIEWER",
  "user_status": "SUSPENDED",
  "user_pw": "new#Guard77"
}
Response 200
{ "user_no": 4 }
Errors
상태코드code설명
403FORBIDDEN일반 사용자가 본인이 아닌 계정을 수정하려는 경우 — "본인 계정만 수정할 수 있습니다."
403FORBIDDEN일반 사용자가 user_role 또는 user_status를 보낸 경우 — "권한 등급과 계정 상태는 관리자만 변경할 수 있습니다."
404USER_NOT_FOUND존재하지 않는 user_no

💡 cctv_stream_url 재생 방법 (HLS)
이 값은 HLS 스트림 주소(.m3u8) 다. 백엔드는 영상을 중계하지 않고 주소 문자열만 전달하므로, 프론트가 카메라(또는 스트리밍 서버)에 직접 연결해 재생한다.
  • Safari · iOS 는 <video src="..."> 로 바로 재생된다.
  • Chrome · Firefox 는 네이티브 지원이 없어 hls.js 가 필요하다: hls.loadSource(cctv_stream_url); hls.attachMedia(videoEl);
  • CORS: hls.js 는 .m3u8 과 .ts 조각을 XHR 로 가져오므로, 스트리밍 서버가 프론트 오리진을 허용해야 한다 (막히면 재생 자체가 실패).
  • 지연: HLS 특성상 5~15초 늦다. AI 는 원본 프레임을 실시간으로 보므로 화재 알림이 영상보다 먼저 도착할 수 있다 — 정상 동작이다.
  • 스트림 주소가 사설망(192.168.x.x)이면 프론트를 띄운 PC 가 같은 네트워크에 있어야 한다.

6. 관리자 알림 (Alerts)

알림 흐름 (v0.3 확정 — 동시 발송, 단계 승격 없음)

이벤트가 CONFIRMED로 확정되면 백엔드는 그 CCTV 의 소유자(cctv.user_no) 한 사람에게 알림을 만든다. ADMIN 전체 브로드캐스트는 없다.

  1. 알림 행 2개를 동시에 만든다 — PUSH와 SMS. 같은 트랜잭션에서 한 번에 INSERT 하므로 alert_sent_at과 alert_deadline_at이 두 행 모두 완전히 같은 값이다. alert_level은 둘 다 1. 실제 문자 발송은 SMS 행에 대해서만 일어나고, PUSH 는 프론트가 GET /api/alerts 폴링으로 가져간다.
  2. 유예는 한 번뿐이다 — alert_deadline_at = alert_sent_at + ALERT_DEADLINE_MIN (기본 3분). 이 유예가 지나면 다음 단계는 119 신고다. 1차→2차 SMS 같은 승격 단계는 없다.
  3. 응답은 이벤트 단위로 적용된다 — 사용자가 PUSH 든 SMS 든 한쪽에만 응답하면, 같은 이벤트의 나머지 미응답 알림도 같은 상태·같은 alert_responded_at으로 함께 닫힌다. 같은 사람의 같은 화재 건이기 때문이다. 이미 닫힌 형제 알림에 다시 응답하면 409 ALREADY_RESPONDED.

그 다음 갈림길은 셋뿐이다.

사용자 행동알림 상태119 신고
READ (화재 확인) — SENT 상태에서 두 알림 모두 READ 즉시 시작 — report_trigger_reason = USER_CONFIRMED
CANCEL (오탐 취소) — 마감 전에만 가능 두 알림 모두 CANCELED 영원히 없음 — 에스컬레이션도 이 이벤트를 건너뛴다
무응답으로 유예 마감 경과 이벤트의 미응답 알림 전부 NO_RESPONSE 자동 시작 — report_trigger_reason = NO_RESPONSE_TIMEOUT

무응답 처리는 백엔드 스케줄러가 ESCALATION_INTERVAL_SEC(기본 10초)마다 도는 에스컬레이션 스윕이 담당한다. 프론트가 호출할 API 는 없다. 스윕은 검출이 끊긴 PENDING 이벤트를 DISMISSED로 정리하는 일도 함께 한다.

💡 늦은 READ — 이미 NO_RESPONSE가 된(=119 신고까지 진행된) 알림에 뒤늦게 READ를 보내는 것은 허용되지만, alert_status는 NO_RESPONSE 그대로 보존되고 alert_responded_at만 기록된다. 늦은 확인이 "무응답으로 신고까지 갔다"는 이력을 지우지 못하게 하기 위해서다. 이 경우 두 번째 신고는 만들어지지 않는다.
💡 점검 모드 — event_is_test = true인 이벤트는 확정되어도 알림 행 자체가 만들어지지 않고, 에스컬레이션·119 신고 대상에서도 완전히 제외된다.

8. 119 신고 (Reports)

신고 흐름 (승계 알고리즘)

신고는 사용자가 만들지 않는다. 백엔드가 두 지점에서 자동으로 시작한다.

report_trigger_reason시작 지점
USER_CONFIRMED사용자가 SENT 알림에 READ(화재 확인)로 응답한 즉시
NO_RESPONSE_TIMEOUT유예 마감까지 무응답 → 에스컬레이션 스윕이 알림을 NO_RESPONSE로 닫으면서

시작되면 아래 순서로 돈다. 바깥 루프가 기관 승계, 안쪽 루프가 같은 기관 재시도다.

  1. 후보 기관 정렬 — agency_is_active = true인 기관을, 해당 이벤트 CCTV 의 좌표(cctv_lat/cctv_lng)로부터의 하버사인(haversine) 거리 오름차순으로 줄 세운다. 활성 기관이 하나도 없으면 신고 자체를 하지 않는다.
  2. 행 선점 — 시도할 기관마다 report_119 행을 먼저 SENDING으로 INSERT 한다. report_sequence는 1, 2, 3… 으로 올라간다. 거리는 report_distance_km(소수 3자리)에, CCTV 위치 문자열은 report_address에 남는다.
  3. 전송 (안쪽 루프) — 그 기관의 agency_endpoint로 신고 JSON 을 POST 한다. MAX_REPORT_ATTEMPTS(기본 4)회까지 시도하며, 매 시도마다 report_attempt_count가 올라간다. 타임아웃(REPORT_HTTP_TIMEOUT_SEC, 기본 3초) · 연결 실패 · 2xx 아닌 응답은 모두 실패로 보고 재시도한다.
  4. 성공 — 2xx 를 받으면 그 행이 DISPATCHED가 되고 report_dispatched_at이 찍힌다. 응답 본문에 external_id가 있으면 report_external_id에 저장한다 (본문 없는 2xx 도 성공으로 본다 — 이때는 null). 여기서 승계는 멈춘다.
  5. 기관 소진 → 승계 — MAX_REPORT_ATTEMPTS회를 다 쓰고도 못 받으면 그 행은 NO_RESPONSE(무응답으로 승계)로 닫고, 다음으로 가까운 기관에 대해 2번으로 돌아간다. report_sequence가 1 늘어난다.
  6. 전 기관 소진 — 마지막 기관까지 실패하면 그 마지막 행만 FAILED(전송실패)가 된다. 앞선 기관들의 행은 NO_RESPONSE로 남는다.

기관에 전송하는 JSON 페이로드는 다음과 같다 (가상 119 서버 mock-119가 받는 형식).

{
  "event_no": 12,
  "address": "본관 정문 앞",
  "lat": 37.5665,
  "lng": 126.978,
  "event_class": "FLAME",
  "confidence": 0.9123,
  "reported_at": "2026-08-08T14:33:10"

🔒 이벤트당 진행 중 신고는 1건뿐이다. SENDING · DISPATCHED 두 상태에 걸린 DB 부분 유니크 인덱스(UX_report_119_active ON report_119(event_no))가 강제한다. 그래서 "사용자 READ"와 "에스컬레이션 무응답"이 동시에 신고를 시작해도 신고는 하나만 나가고, 나중에 도착한 쪽은 이미 진행 중인 신고를 그대로 돌려받는다. NO_RESPONSE · FAILED는 활성 상태가 아니므로 승계 이력은 얼마든지 쌓일 수 있다.

누적·확정 규칙
  1. 열린 이벤트 찾기 — 해당 카메라의 가장 최근 PENDING 이벤트를 찾는다.
  2. 끊김 판정 — 그 이벤트의 마지막 활동 시각(가장 늦은 media_captured_at, 없으면 event_first_detected_at)이 captured_at보다 EVENT_WINDOW_SEC(기본 60초) 넘게 오래됐으면 그 이벤트를 DISMISSED(기준미달)로 닫고 없는 것으로 취급한다. 같은 정리를 에스컬레이션 스윕도 주기적으로 수행한다.
  3. 비화재 프레임 — flame/smoke가 하나도 없으면 누적도 미디어 저장도 하지 않는다. 열린 이벤트가 없으면 {"event_no": null, "ignored": true}, 있으면 현재 상태를 그대로 돌려준다.
  4. 이벤트 생성 / 누적 — 열린 이벤트가 없으면 PENDING 이벤트를 새로 만들고 (event_detected_frames = 1), 있으면 +1 한다. event_class는 병합되고(FLAME + SMOKE → FLAME_SMOKE), event_confidence는 지금까지의 최고값을 유지한다.
  5. 미디어 저장 — 화재 프레임은 event_media에 media_type = FRAME으로 저장되고, detections 배열은 원본 그대로 media_detections에 들어간다. 지금까지 중 가장 신뢰도가 높은 프레임이 대표 이미지(media_is_primary)로 교체된다.
  6. 확정 — event_detected_frames >= event_threshold_frames가 되는 순간 CONFIRMED로 바뀌고 event_detected_at이 찍히며, 곧바로 알림 발송(PUSH+SMS)이 이어진다 (6번).
💡 event_threshold_frames는 이벤트를 만드는 순간의 EVENT_THRESHOLD_FRAMES(기본 30) 값을 그 이벤트 행에 복사해 둔 것이다. 설정을 바꿔도 이미 열려 있는 이벤트의 기준은 바뀌지 않는다. 확정된 이벤트는 더 이상 "열린 이벤트"가 아니므로, 그 다음 화재 프레임은 새 이벤트를 연다.
Response 200 — 누적/확정
{
  "event_no": 12,
  "event_status": "PENDING",
  "event_detected_frames": 7,
  "event_threshold_frames": 30
}

임계값에 도달한 호출에서는 "event_status": "CONFIRMED"로 내려온다.

{ "event_no": null, "ignored": true }

10. 미디어 파일 서빙

GET /media/<path> 인증 불필요
검출 프레임 이미지(FRAME)와 영상 클립(CLIP) 파일을 그대로 내려준다. 유일하게 /api 아래가 아닌 경로다.
URL 매핑

API 응답의 media_url · thumbnail_url 값은 이미 /media/로 시작하는 완성된 경로다. 프론트는 가공 없이 그대로 쓰면 된다.

event_media.media_url : "/media/events/12/frame_001.jpg"
실제 파일             : <MEDIA_ROOT>/events/12/frame_001.jpg
브라우저 요청         : GET http://localhost:5000/media/events/12/frame_001.jpg

<img src="/media/events/12/frame_001.jpg">   <!-- 이대로 동작 -->

MEDIA_ROOT(환경변수, 기본값은 프로젝트 루트의 media/) 아래의 파일만 나간다. ../나 절대경로로 루트 바깥을 노리는 요청은 404 로 막힌다.

Errors
상태코드code설명
404NOT_FOUND파일 없음 또는 경로 탈출 시도. 본문은 공통 에러 형식 { "code", "message" }
⚠️ 인증을 걸지 않은 것은 의도된 시연 범위의 결정이다. 브라우저의 <img>/<video> 태그는 Authorization 헤더를 붙일 수 없어서 JWT 를 요구하면 화면에 이미지가 뜨지 않는다. 운영 환경이라면 (1) 만료 시간이 든 서명 URL(signed URL)을 발급하거나 (2) nginx 등 리버스 프록시에서 인증 후 내부 리다이렉트(X-Accel-Redirect)로 넘기는 방식이 필요하다. 지금 구조는 경로만 알면 누구나 파일을 열 수 있다는 뜻이니 그대로 배포하지 말 것.
💡 thumbnail_url이 가리키는 것 — 해당 이벤트의 대표 프레임 (media_is_primary = true) 중 media_confidence가 가장 높은 것, 동점이면 media_no가 작은 쪽(= 먼저 저장된 프레임)이다. 대표 프레임이 없으면 null이 내려온다.

※ 미정 사항: 실시간 알림 전달 방식의 최종 확정(백엔드 권장안은 GET /api/alerts 3~5초 폴링), 대시보드 통계 API 필요 여부.
※ v0.2 반영 내역: users PUT 권한 규칙, 잘못된 파라미터 400 통일, 알림 늦은 READ 규칙, user_phone 숫자만 저장, user_id·비밀번호 작성규칙.
※ v0.3 반영 내역: 내부 검출 수집 API(POST /api/internal/detections, X-Internal-Key 인증) 신설, event_status에 PENDING 추가, 알림 단계 승격 폐기(확정 시 PUSH+SMS 동시 발송·alert_level은 항상 1), 알림 응답의 이벤트 단위 적용 규칙, 119 신고 승계 알고리즘(하버사인 거리순 · 기관당 최대 4회 · 이벤트당 진행 중 신고 1건), 미디어 파일 서빙(GET /media/<path>, 무인증 — 시연 범위 결정) 문서화, 환경변수 부록 추가, cctv_stream_url을 HLS(.m3u8)로 확정하고 재생 방법·CORS·지연 주의사항 명시.
